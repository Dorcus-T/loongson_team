## 二、OpenSTA 静态时序分析（Nangate45 45nm, 100MHz 目标）

> 工具: OpenSTA 2.0.17 + Nangate45 liberty
> 时钟: aclk, 10ns period, 0.3ns setup uncertainty

### 真实 Timing 汇总

| 指标 | 数值 | 说明 |
|------|------|------|
| WNS (过滤后) | **-4.80 ns** | 排除多周期假路径后 |
| 最长真实路径 | **14.3 ns** | ALU 乘法器数据通路 |
| 等效 fmax | **~70 MHz** | 45nm 工艺，实际可更高 |
| Clock uncertainty | 0.3 ns | 设置量，可根据实际抖动调整 |

> **注意**: 原始 WNS = -378ns 来自串行除法器的多周期反馈路径。STA 将除法的 32 拍迭代当作纯组合逻辑分析，这是假违规。真实关键路径是 14.3ns 的乘法器通路。

### 路径特征分析

| 特征 | 数值 | 占比 |
|------|------|------|
| 总延迟 | 14.303 ns | 100% |
| 门延迟 (cell delay) | ~3.2 ns | ~22% |
| 线延迟 (net delay) | ~11.1 ns | **~78%** |
| 最大扇出 | **151** | — |
| 最大 net 电容 | 359 fF | — |

**关键发现**: 线延迟占总延迟 78%，主要原因是 `alu_src2[3]` 信号的扇出高达 **151**（驱动 151 个门）。这是 64×64 乘法器的 Booth 编码输入总线，每位需要驱动大量部分积生成单元。

线延迟:     ████████████████████████████  78%  ← 主要瓶颈

## 三、关键路径分析（按概率排序）

### 🔴 高危 1：ALU — 乘法器 + 结果选择 OR 树

**文件**: `alu.v:263-279`

64×64 有符号/无符号乘法器是纯组合逻辑，产生 2,766 XOR + 1,618 XNOR（通用门）：
- 乘法器内部（Wallace/Dadda 树）：~12-15 级门延迟
- 19 路结果选择 OR 树：~3-4 级 MUX2 延迟
- **总计约 15-20 级门延迟**

```verilog
// alu.v:263 — wide OR-tree，19 路 32-bit 信号归并
assign alu_result = ({32{op_add|op_sub}} & add_sub_result)
                  | ({32{op_slt       }} & slt_result)
                  | ({32{op_sltu      }} & sltu_result)
                  // ... 共 19 路
```

400MHz vs 100MHz 时 ALU cell 数增长 10.5%，进一步印证此模块是瓶颈。

### 🔴 高危 2：TLB — 32 路全相联 CAM 查找

**文件**: `tlb.v`

- 32 路并行的虚拟地址比较器（每路比较 VPPN[31:13] 共 19 bits）
- 比较结果 → 命中检测 → 32→1 优先级编码器 → PPN 读出
- 7,361 MUX（通用门），OAI21: 5,496，NAND3: 2,922
- **总路径约 10-15 级门延迟**

### 🟡 中危 3：ID 阶段 — 数据前递路径（跨级旁路）

**文件**: `mycpu_top.v` + `id_stage.v`

这是跨越流水级边界的纯组合路径，不经过流水线寄存器：

```
EX: ALU 结果 (最慢是乘法)
  → ex_to_id_result  --------+
MEM: 访存结果                  |
  → mem_to_id_result -------+ |
WB: 写回结果                  | |
  → wb_to_id_result ------+ | |
                           v v v
ID: regfile 读端口 → forwarding MUX → operand → 下一个 EX 的 ALU
    (1,600 MUX2)    (326 MUX2)
```

**如果乘法结果（EX 拍）需要前递给下一条指令（ID 拍），这是整条 pipeline 里最长的纯组合路径。**

### 🟡 中危 4：CSR 寄存器读路径

**文件**: `csr.v`

- 30+ CSR 寄存器，读地址译码后选择对应寄存器值输出
- 读地址译码（726 AOI3）→ 优先级 MUX
- 写后读冒险需要在 ID/EX/MEM/WB 四级之间追踪 CSR 写
- **路径约 8-12 级门延迟**

### 🟢 低危 5：Cache Tag 比较 + AXI 桥

- 2 路组相联：2 路并行 tag 比较（20 bits）→ way 选择 MUX
- cache_axi_bridge 在 400MHz 时 cell 增长 12.7%，但绝对值不大（5,066→5,711）
- 这些模块通常不是 CPU 主频瓶颈（SRAM 访问有独立时序约束）

## 四、优化建议

### 1. 乘法器流水化（最有效，优先级最高）

当前 64×64 乘法器是一拍纯组合逻辑。**加 2-3 级流水**可以把 15-20 级门延迟拆成每拍 4-6 级。

```verilog
// 建议：类似除法器的握手方式
// EX 阶段发 mul 请求 → 内部 2-3 拍产生结果 → 写回
// 需要: stall 信号 + 乘法状态机
```

- fmax 提升预估：**50-100%**（假设乘法器当前是瓶颈）
- IPC 影响：很小（乘法指令密度通常 < 1%）
- 实现难度：中等

### 2. ALU 结果 MUX 平衡化

`alu.v:263` 的 19 路 OR 归并改为平衡二叉树：

```verilog
// 当前: 19 路线性 OR（深）
// 改为: 2 级平衡树
wire [31:0] result_group0 = (...) | (...) | (...);  // 6-7 路
wire [31:0] result_group1 = (...) | (...) | (...);
wire [31:0] result_group2 = (...) | (...) | (...);
assign alu_result = result_group0 | result_group1 | result_group2;
```

- 延迟减少：~2 级门延迟（19→1 级联 OR 改为 3 路并行 → 1 级归并）

### 3. TLB 查找加一级流水寄存器

- 第 1 拍：CAM 比较（32 路并行）
- 第 2 拍：命中编码 + PPN 读出

对于 5 级流水 CPU，TLB 访问在 EX 阶段，如果加一级流水需要把地址翻译推迟到 MEM 阶段——改动较大，**建议先确认 TLB 是否真的在关键路径上再改**。

### 4. 前递路径优化

如果前递被 STA 确认为瓶颈：
- 在前递信号上插入寄存器（接受 1 拍转发延迟，编译器/调度器可掩盖）
- 或者限制哪些指令结果参与前递（例如乘法结果不参与前递，强迫通过寄存器堆转发）

## 五、获取精确时序数字

当前 Yosys + Nangate45 只能得到逻辑级数和相对延迟。要获得**带真实 ns/ps 延迟数字的关键路径报告**，还需要：

### 方案 A：OpenSTA（开源 STA）

```bash
# 安装
sudo apt install opensta

# 已有: Yosys 生成的门级网表 (outputs/synth_nangate.v)
# 已有: Nangate45 liberty (libs/NangateOpenCellLibrary_typical.lib)
# 已有: SDC 约束 (mycore.sdc)
# 缺少: 只需写一个 OpenSTA 启动脚本
```

### 方案 B：Vivado/Quartus（如果有 FPGA）

```tcl
# Vivado 示例
read_verilog [glob ../*.v]
synth_design -top core_top -part xc7a100tcsg324-1
report_timing -max_paths 20 -file critical_paths.rpt
report_timing_summary -file timing_summary.rpt
```

FPGA 时序报告虽然与 ASIC 不同（布线延迟主导），但**找组合逻辑路径长度的能力是一致的**，且更接近硬件真实行为。

### 方案 C：Vivado 免费版 + 软核

即使没有 FPGA 板，Vivado 也能跑综合+时序分析（不需要 bitstream 生成和硬件）。
